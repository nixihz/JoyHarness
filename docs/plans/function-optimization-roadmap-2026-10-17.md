## 先看这一页

**建议先把“拿起任意一只控制器就能可靠操作当前应用”做完整，再扩大智能体接入。** 当前产品已具备手柄键鼠、应用 Harness、六槽 Micro 控制、遥控器语音、屏幕光缝和自动更新。近期收益主要来自输入可靠、配置不串、操作入口完整、故障可解释。

| 顺序 | 要交付的结果 | 为什么先做 |
|---|---|---|
| 1. 稳定现有输入 | 完成 Joy-Con 与指针改动的验收，补齐运行时状态写入失败反馈 | 用户一旦遇到漂移、失灵或错误状态，就无法信任后续操作；本地已有改动应先收尾 |
| 2. 让映射可预测 | 标准手柄家族独立配置；补齐 #8 的系统默认档；单 Joy-Con/遥控器也能呼出 Harness 切换 | 当前存在配置共享、未匹配应用沿用旧 Harness、部分设备没有切换入口等具体缺口 |
| 3. 降低使用门槛 | 按实际能力显示连接提示，补充语音自检与本地诊断导出，再增加配置备份 | 现有能力足够丰富，但恢复路径分散，新用户不容易判断缺什么 |
| 4. 验证下一条增长路线 | 优先验证不依赖 RP2040 的一次性完成提醒；其后再评估 Cursor/Pi 状态适配 | 有已有研究可复用，但原生未读、六槽顺序和跨进程状态仍不能承诺 |

**下一轮建议只承诺三项：O01 输入收尾、O02 状态写入可靠性、O09 中的文档与验收基线。** 随后进入 O03/O04/O05 配置与切换体验。不要在同一轮同时改动输入、配置迁移和智能体协议。

## 2. 目标用户、目标与假设

核心用户是希望离开键盘仍能操作本地智能体的 macOS 用户，尤其是单手 Joy-Con、沙发场景遥控器，以及多应用/多控制器切换用户。典型任务是：移动与滚动、切到正确应用、执行已理解的快捷操作、按住说话、发现任务需要关注。

规划围绕四个结果：**输入可靠、行为可预测、遇阻可恢复、扩展有边界。** 当前没有采用率、活跃用户数、故障率或上手耗时的可信统计，不以下载次数替代这些指标；度量方案见第 6 节。

| 假设 | 当前依据 | 验证方式 |
|---|---|---|
| 现有控制体验比增加 Agent 数量更紧急 | 连续输入修复、本地工作量、映射文档已记录的缺口 | 维护者日常使用记录 + O01 真机矩阵；不是市场调查结论 |
| 一个维护者是主要实施资源 | 未提供团队规模 | 按单人串行交付估量；增加人手时优先并行做文档、平台验证，不并行修改同一映射存储 |
| 单手/遥控器用户需要独立完成切换 | K04/K05 缺入口，已有设备支持 | 使用各设备独立走完切换、取消、回到映射模式 |
| 无硬件提醒有助于降低尝试成本 | 绘制已独立于硬件；研究指出状态同步缺口 | 先验证准确率和可理解性，再判断是否发布；不预估用户增长比例 |

### O01：完成输入修正，不提前摘掉实验性标记

作为单手或双手柄用户，我希望轻推、转向、回中和切换握姿都符合预期，以便连续控制鼠标而无需反复校正。

交付重点是检查已有实现、补齐遗漏和真机结果，不重新实现已完成的 HID 校准。保留当前设计中指针直接跟随偏移、滚动独立平滑、斜向速度归一化，以及配置变化刷新映射缓存的目标。

验收标准：

- Joy-Con L/R 各覆盖横握、竖握；双支覆盖配对与其中一支断开。记录硬件、macOS、应用提交、连接方式和实际结果。
- 四向/斜向、轻推/满推、回中/反向、L3、SL/SR 与功能层均以**最终鼠标/滚动/按键行为**验证；不只比对解析函数返回值。
- 保持鼠标拖拽、修饰键或语音键时断开、进入原生模式、切换 Harness、呼出浮层：旧输出释放，恢复后不补发旧按下。
- 核对修改映射、恢复默认、换 Harness/家族后下一次输入使用新配置；缓存不能让界面与行为脱节。
- 在后台、显示器切换和 60Hz/高刷新率条件下记录延迟及抖动。硬件未覆盖的组合继续标“未验证”，不改写成全面支持。

### O02：把可靠性落实到实际运行路径

作为遇到异常的用户，我希望知道状态读取/写入是否失败，以便区分设备断开、权限不足与程序自身故障。

交付：统一真实运行时状态写入与可观测错误路径，校对 DTO 覆盖的字段；不要直接切换到现有 DTO 后丢失运行时额外字段。连接详情给出失败原因、最近成功时间与适当恢复入口。

验收标准：

- 通过运行时实际调用路径注入目录不可创建、写入拒绝、编码失败；产生可查错误，旧快照不能继续被解释为本轮成功。
- 保留原子写入、六槽、协议兼容字段，以及 fresh/stale/unavailable 的区别；恢复成功后清除当前故障。
- 错误反馈不得依赖“恰好写不进去”的同一状态文件才能展示，也不能让输入循环反复阻塞或刷日志。
- 有界 socket/串口入队成功仍只表示本地接纳，不使用“任务已执行”作为成功提示；本项不引入固件 ACK 协议。

### O03：同一应用里，不同手柄可以各自定制

作为同时使用 Xbox 和 DualSense 的用户，我希望给其中一只改键时另一只保持不变。

交付：按“应用配置档 × 控制器家族”隔离标准手柄映射，保留 Joy-Con 三类与遥控器已有边界。第一阶段不扩到同型号每一只物理设备的独立配置。

验收标准：

- 在同一 Harness 下分别给 Xbox/DualSense 配置不同动作、应用目标、录制快捷键与备注，交替输入、重连、重启后各自保留。
- 旧共享配置迁移时，保留所有显式自定义，重复迁移不覆盖后续修改；无法区分“用户刻意设成旧默认”与“未改过”的数据要写清保守策略。
- 恢复默认仅影响当前应用与当前家族，确认文案同时写出这两个范围；取消后数据不变。
- 先记录 ADR，再统一 `CONTEXT.md`、映射清单与迁移实现。完成后才能进入 F01 的备份/模板格式设计。

### O04：补齐 #8，同时解决旧需求与当前契约的冲突

作为跨应用用户，我希望进入未配置的应用后使用明确的通用配置，避免继续发出上一应用的专属操作。

交付：不可删除、无关联应用的系统默认档；通用键鼠默认值；前台无匹配时回退；UI 明确当前生效/正在编辑的配置。它是通用配置例外，不是新增的应用 Harness：首版仅用于自动兜底和设置选择，显示“系统默认”及中性系统图标，不作为应用卡加入 PS/Home 浮层。此例外纳入 ADR 并同步领域文档。已有自定义应用添加、去重、图标、持久化与切换复用现有实现。

验收标准：

- Codex → 未配置浏览器 → Claude 的切换结果可预测；系统默认不包含 Codex Micro、Claude 会话等专属动作，选择它不启动应用。
- 切换前释放持续输出；旧应用自定义、应用目标、快捷键备注不丢失；系统默认不会复制旧 Codex 专属映射。
- 设置窗口自身获得焦点时，不立即冲掉用户刚选的编辑配置；原生模式的输入暂停优先级不被破坏。
- 为“多义终端/身份不唯一”写出一致策略，并覆盖重启、匹配冲突、应用被移除等场景。

**需要先修订的冲突：** #8 要求无唯一匹配时进入系统默认，而当前 `CONTEXT.md` 要求多义终端保留手动选择；#8 中“自定义应用不进切换浮层”“激活行为可设置”等旧边界也与当前已发布行为不符。建议保留现有自定义应用浮层及确认后激活行为，采纳系统默认兜底方向；多义终端策略由维护者在 O04 开始时决定并记 ADR。不能仅凭 `ready-for-agent` 标签把旧文本全部照做。

### O05：每种设备都能独立完成模式与 Harness 切换

作为只拿一只 Joy-Con 或遥控器的用户，我希望不用先拿另一只手柄，就能切换应用。

交付建议：新增可映射的“打开 Harness 切换”动作，让没有固定 PS/Home 入口的设备可选用；在现有原生模式设置页增加明确的“进入原生模式 / 恢复映射”操作，并引导用户为当前设备绑定已有的模式切换动作。默认键位先验证，避免直接覆盖遥控器 Home=Esc、Menu=模式切换等已有习惯。

验收标准：

- 单 Joy-Con L、单 Joy-Con R、遥控器都可完成呼出、导航、确认与取消；呼出那次按键不穿透到目标 App。
- 浮层关闭后等待对应物理按键释放，再恢复映射；设备断开时关闭浮层并清理持续输出。
- 原生模式下 PS/Home 仍先恢复映射，不与映射模式的“打开浮层”混淆；设置、帮助和映射预览文案一致。
- 在不属于白名单的应用中，标准手柄、单 Joy-Con L/R、遥控器均通过明确的设置入口或首次绑定步骤完成“手动进入原生模式→恢复映射”；记录各设备的入口，不把仅改帮助文案算作 K06 完成。
- 第一版不依赖长按/双击新手势。若未来引入，需要先验证单击延迟、重复触发及冲突。

### O06：已有能力按用户当前任务呈现

交付建议：在空状态和连接详情中组织短指引：连接设备 → 验证按键 → 授予必要权限 → 按需启用 Micro/光缝或遥控器语音。通用设置先放基础控制与启动项，再放可选扩展；沿用原生表单，不新建大型引导系统。

验收标准：

- Claude/通用键鼠场景没有 RP2040 时仍说明可用能力；用户尝试 Micro 操作或启用光缝时，才就近解释所需适配器/固件。
- 现有配置若含不适用于当前 Harness 的动作，界面解释其不可用原因，不只保存后静默无效；保留必要的释放与归零行为。
- 无设备、未授权、权限撤销、状态陈旧各有不同的文字/图标和下一步。权限返回后以真实状态刷新。
- 只做键鼠的用户可以跳过麦克风与 RP2040 设置；不把可选组件变成上手前置条件。
- 键盘与 VoiceOver 能完成基础设置；中英文、亮/暗、高对比和 Reduce Motion 符合既有设计规范。

### O07：让用户能判断语音在哪一段中断

交付建议：现有连接详情增加按需语音检查，依次展示遥控器连接、语音流、虚拟麦克风组件、系统当前输入，以及目标工具是否由对应快捷键触发。提供脱敏的本地诊断导出，供用户自行查看或附到 issue。

验收标准：

- 明确区分“组件未安装/需更新”“BLE 未就绪”“当前未选该输入”“目标录音入口需检查”；Joy Harness 无法观察目标应用录音状态时直接说明，不能伪造成功。
- 连续说话、快速按放、句尾缓冲、断连、原生模式切换、组件安装取消均有真机记录；音频尾部未播放完时不提前释放相应录音按键。
- 自检不默认改全局输入，也不自动安装组件；显式选择后才执行对应设置动作。
- 默认导出仅含版本、设备能力、权限、连接/错误阶段与时间；不含任务正文、语音内容、凭据或完整用户目录。导出前可预览，本项不做自动上传。

### O08：把“默认键位”当作产品配置维护

交付建议：逐个核验目标应用真实快捷键，再决定空键是否需要补默认；修正 DualShock Share 标签、实际功能层名称及恢复默认影响范围。飞书截图提供明确适用条件或改用通用截图模板，不依据“所有键都应有动作”填满映射。

验收标准：动作有目标 App/版本与核验记录；应用不存在时结果可解释；新默认值不覆盖用户自定义；恢复默认、设置展示与文档同源核对。重复的触控板左键可能有操作价值，K07 先做使用验证，不直接判为浪费。

### O09：让版本、文档和真机证据对得上

交付：更新当前映射清单，建立简短的发布验收矩阵，补充应用/固件/麦克风组件的能力与更新关系。现有 CI、签名公证、双架构打包已经存在，不重复立项。

验收标准：

- 同步 Joy-Con K03 及 J 系列表格、H03 的应用激活说明、标准家族隔离说明和指针刷新策略；不能继续以历史文档覆盖当前实现。
- 对光缝明确“应用已更新但固件无 Report 7”的状态和处理路径；协议文档补齐 Feature Report 7，不把串口握手成功当全部能力就绪。
- 发布说明移除已废弃 hooks/notify 等安装描述；兼容性矩阵记录实际测过的 macOS/芯片/设备/连接方式，未覆盖项保持未知。
- 产品改动交付时执行适用的 `task ci`、`task release-check`；涉及固件时执行 `task firmware`，并验证发布包搬离构建目录后能启动。应用支持 macOS 13 不等于最新 macOS CI 已证明旧系统兼容。
- 在前一已签名稳定版上验证真实 Sparkle 升级，覆盖两种架构、更新取消与麦克风组件需单独更新的提示；CI 成功不能代替实际安装验证。

### O10：使退出、停止与重新启动具有完整契约

当前 `applicationWillTerminate` 调用 `stopHotkeys()`，它会清理部分灯效、快捷键和遥控器资源，但未完整调用运行时启动的鼠标、控制器、Joy-Con motion、RP2040、线程 provider、socket、监控与计时器的停止路径；前台应用观察者的 token 也未保存。这是与已接受的可靠性规格 R6 的差距，**不是本次已经观测到进程泄漏或退出后仍发送事件**。

交付：统一幂等的 runtime stop，保存并注销观察者，按照依赖顺序释放持续输入、关闭 I/O、停止子进程与计时器。普通进程退出由系统回收资源不能替代应用级释放及可重复生命周期保证。

验收标准：

- 对真实 runtime 接线验证启动→停止→再启动；停止后 socket 不再接受控制、provider 不再重启、计时器及迟到回调不再产生副作用，再启动无重复输入/观察回调。
- 退出前先释放持续输出，再关闭对应通道；RP2040 需有界地处理待发松开命令，不能先断开后丢弃释放。没有端到端 ACK 时明确保留“无法确认目标接收”的边界。
- 多次停止、启动未完成时停止、依赖启动失败后停止均安全；停止后清理实例锁与监控，使下一次合法启动可成功。
- 关闭 Dashboard 窗口仍按现有设计后台运行；只有停止/退出才执行完整清理，避免把关窗口误改成退出应用。
- 睡眠唤醒、设备拔插与应用重启分别记录恢复行为；子组件单测之外补运行时集成证据。

## 4. 未来功能路线

以下均为建议，不是现有能力。每条都设验证条件，避免把研究文档中的“可能实现”直接排成正式发布日期。

| ID | 方向 | 建议顺序 / 粗估规模 | 最小可交付范围 | 进入正式开发的条件 |
|---|---|---|---|---|
| F01 | 本地配置备份、导入与场景模板 | 优先 / L | 导出单个应用×家族配置；导入预览差异、选择覆盖范围、恢复；先提供通用办公/语音辅助模板 | O03/O04 存储稳定，有真实重装/换机/复用需求 |
| F02 | 无 RP2040 的软件完成提醒 | 优先验证 / 3–5 日研究，开发待估 | 首轮只做本机任务“完成一次，提醒一次”，清楚区分硬件光缝 | 证明状态来源有效、去重/重启/中止不误报；先更新 ADR/CONTEXT/DESIGN |
| F03 | Cursor/Pi 状态适配 | 后续 / 单 provider 3–5 日验证，开发待估 | 先选一个 provider，观察既有会话状态；不接管 prompt 或审批 | 复核当前版本协议与生命周期；定义 provider+session 身份和陈旧状态 |
| F04 | Cursor/Pi 双向控制 | 远期 / XL，验证后再估 | 单 provider 单会话的明确控制流程，再考虑并发 | F03 通过且用户确需；确认 Joy Harness 是否扩展到进程/会话所有权 |
| F05 | 按设备校准与单手输入增强 | 后续 / M–L；陀螺仪另估 | 校准来源可见、死区/响应曲线预览；优先解决经测量确认的差异 | O01 有基线，证明固定设置仍不够；不替换当前良好默认 |
| F06 | 固件能力检查与升级辅助 | 后续 / M–L | 检测能力版本、展示兼容关系、引导手动刷写，提供明确恢复步骤 | O09 能力矩阵稳定；协议兼容与失败恢复有实测 |

### F01：可携带的个人控制方案

价值：重装或更换设备后不再重新录制全部快捷键，也便于验证候选默认布局。首版只做本地文件，不建账号、云同步或模板市场。

验收门槛：格式包含版本与适用家族；预览新增/覆盖/不可用动作；导入取消不修改；损坏文件与不支持版本不产生部分写入；导入再导出保持用户语义；仅还原选定范围，不携带授权状态或敏感本地信息。

### F02：先证明提醒可信，再谈无硬件六槽

2026-10-14 的[既有调研](../research/codex-edge-lights-software-mode.md)指出：独立 app-server 的 `notLoaded` 不代表任务空闲；历史元数据/rollout 不能完整表达桌面客户端的未读、等待审批和跨主机状态。绘制与预览可以无硬件运行，不代表原生六槽可直接软件替代。

验证分两道门：

1. **一次性完成提醒**：明确支持的本机任务范围；采集开始/完成/中止/重启与日志重放样本；确认不重复、不把中止算完成，未知时不报确定状态。手动确认/超时收起属于软件提醒语义，不称为“已在 Codex 读过”。
2. **完整六槽候选**：只有能验证原生槽位对应、等待/运行/完成、跨入口阅读后的消除，以及七个以上任务的稳定选槽，才考虑完整体验。否则保留硬件模式，或明确发布独立的软件规则。

验收指标先用受控事件回放和少量本机试用；没有真实结果前，不宣称“替代 Micro”。点击打开任务的 deep link 也需验证版本与主机范围。原生审批、拒绝、PTT 不包含在本项内。

### F03 / F04：先增加兼容能力，再决定是否成为 Agent 宿主

[Cursor/Pi 调研](../research/cursor-pi-agent-integration.md)日期为 2026-08-23，是候选方案来源，需要在立项时重验。当前 Harness 代表应用映射，不等于已支持 ACP/RPC 会话控制。

- F03 只选一个 provider 和一种受支持运行形态，定义状态来源、版本、失联/过期策略、事件去重和卸载流程。安装适配时合并用户原配置，不覆盖已有 hooks/extensions。
- 状态展示仍遵守 Dashboard 边界。若需要新的提醒入口，先更新设计契约；不得沿用旧调研“状态变化自动震动”的建议，因为当前版本刻意限制为有限且明确触发的反馈。
- F04 会改变当前“不拥有任务执行”的领域边界，须先做产品决策及 ADR。Cursor 的 permission request、Pi 自建阻断机制、问题回答和计划确认不能抽象成一个无上下文的“批准”。
- 最小验收覆盖请求身份、目标说明、一次决定、过期/取消/断连、并发隔离与恢复；不能把本地已接纳视为外部动作完成。单会话通过后才考虑六槽并发。
- 跨 provider 语音需要独立的录音/转写/发送方案；现有 Micro `ACT10` 无法直接复用，暂不捆绑。

### F05 / F06：用证据决定是否深化硬件能力

Joy-Con IMU 数据存在不代表已经有可用的陀螺仪鼠标。先测静置漂移、按住启用/释放、重连校准和能耗，只有明显改善单手指向才推进。开放死区/响应曲线前需同步 `DESIGN.md` 当前固定 10% 死区的契约。每物理设备独立档和更多控制器型号也应由实际需求驱动。

固件辅助优先解决“我需要哪个版本、当前缺哪项能力、如何恢复”。自动刷写、CDC ACK/重试属于后续独立设计；ACK 需要明确幂等与重复输入防护，不能用盲目重试修补不确定执行结果。

## 5. 实施顺序与资源假设

按 **1 名主要开发者、每周约 5 个有效工作日**作粗排，包含开发与回归但不保证硬件/外部依赖等待时间。以下是依赖顺序，不是从 10 月 17 日起自动开始的日程；正式版本号由发布流程根据实际范围决定。

| 阶段 | 建议工作量窗口 | 范围 | 阶段出口 |
|---|---|---|---|
| M0 输入与可靠性收尾 | 3–5 周 | 先 O01、O02、O09 的文档/验收基线，再 O10 | 本地已有改动得到逐项结论，核心输入、状态写入与 runtime 生命周期可验证；未测硬件仍标未知 |
| M1 配置与单手闭环 | 3–5 周 | O03 → O04 → O05；同步 O09 相关文档 | 迁移不丢配置、未知应用行为明确、三类单手设备可独立切换 |
| M2 上手与恢复 | 2–4 周 | O06、O07、O08 与 O09 剩余部分 | 用户能判断受阻原因，语音链路可定位，诊断信息可自行导出 |
| M3 选择一个扩展方向 | 3–5 日验证或 6–10 日 F01 实施 | F01 与 F02 按需求择一；F03 次之 | 配置复用可交付，或软件提醒有继续/终止结论；不同时开展三个研究项目 |
| M4 更深集成 | 暂不承诺 | 经验证的 F02 后续、F03/F04、F05/F06 | 由实测价值、接口稳定性和维护成本决定是否立项 |

窗口按清单规模保守留余量，不能把所有上下界相加视为发布日期。若容量只有两周，优先完成 O01 中已有修正的验证、O02 最小闭环和必要文档；其余留在下一轮。

关键依赖：**O01 → 输入基线；O03 → O04 → F01；O02 → O07；O09 → F06；F03 验证 → F04 决策。** F02 的研究可以独立于主线，但不得为了加快研究直接更改当前硬件光缝语义。

## 6. 成功指标与验收方法

以下数值是**建议的验收样本与目标，尚无本次实测基线**。先记录基线，再在各阶段开始时确认阈值；不以静态代码存在替代体验数据。

| 结果 | 采集方式 | 建议验收目标 |
|---|---|---|
| 配置不串、不丢 | 旧配置样本 → 迁移 → 修改 → 切换 → 重启，比较用户可见行为 | 受测样本 0 次错误覆盖；覆盖动作、快捷键、备注、应用目标与明确禁用项 |
| 持续输入可靠释放 | 每种已宣称支持的组合执行断连/模式切换/浮层/退出场景，至少 20 轮 | 0 次残留鼠标按下、修饰键或 PTT；任何可复现残留阻断交付 |
| 指针响应没有回退 | 固定硬件/系统/刷新率下采集输入事件到输出提交的 p50/p95，并记录真实指针体验 | 基线待测；区分应用内耗时和端到端延迟。高亮 `<16ms` 是既有设计目标，不等同蓝牙端到端承诺 |
| 上手路径清晰 | 建议 5 位未配置过的用户或维护者按全新配置复演，记录完成时间和受阻点 | 候选目标：至少 4/5 独立完成“连接→授权→移动/滚动”；5 分钟为待验证目标，配对等待单独记录 |
| 语音稳定 | 设备/系统矩阵下每组至少 20 次短句与长句，含快速重按及恢复 | 记录无声、尾句截断、按键未释放次数；这些场景出现可复现失败时不宣称该组合稳定 |
| 软件提醒可信 | F02 受控事件回放：完成、中止、重复事件、重启、过期，至少 100 个样本 | 受测确定事件无重复/错误完成提醒；未知场景明确降级。真实漏报率仍需试用统计 |
| 后台资源有界 | 空闲、持续输入、六槽特效、BLE 语音各跑固定时长并记录 CPU/内存/唤醒 | 先建基线；无持续内存增长、关闭功能后相应定时器停止；性能预算待基线确定 |

测试原则：验证外部行为与失败边界，遵守 **No tautological tests**。例如迁移测试从历史数据出发核验用户配置，而不是把生产默认表复制成测试期望；状态测试走运行时故障路径，而不是只证明同一个 DTO 能自编码再解码。

共同完成条件：适用测试通过、真机矩阵有记录、文档与实际版本一致、用户自定义保留、回退/失败行为清晰。UI 改动另验键盘、VoiceOver、长名称、两种语言、亮暗/高对比/Reduce Motion；不为纯文档调整增加没有实际价值的单元测试。

## 7. 范围与暂缓事项

近期范围是当前 macOS 产品、现有控制器、应用映射、Micro 硬件路径、遥控器语音与安装恢复。保持六槽领域模型、Codex 动作隔离、原生模式输入所有权，以及设置中选择不激活应用/浮层确认后激活应用的契约。

暂不纳入主线：

- Windows/Linux/iOS 客户端、云账号与配置同步、模板市场、通用脚本/宏执行引擎。
- Dashboard 任务列表、进度卡片或任务跳转区。现有独立光缝例外不等于允许扩大 Dashboard 内容。
- 将无硬件模式包装成原生 Micro 的完整替代；跨主机/云端任务状态未验证。
- DualSense 蓝牙麦克风、Xbox 手柄耳机口在 macOS 的驱动逆向；现有研究不能支撑近期可交付承诺。
- 为了填满映射而添加未知快捷键；循环任务震动；更多装饰特效；#1 游戏彩蛋。
- 全面重写架构。仅在上述验收无法通过当前边界实现时，做必要的接口或模块调整。

## 9. 交付与维护方式

本计划是规划入口；具体实施事项仍以 `nixihz/JoyHarness` 的 GitHub Issues 为准。O/F 编号仅用于本文追踪，不冒充已创建工单。本次未新增、修改或评论 issue，也未创建 PR。

建议每项启动时记录：关联 issue、负责人与验收者、受影响配置/硬件、设计决策、可测试标准、预计规模、回退方式。#8 先更新“已完成/剩余/已过时”部分；新增问题先去重，再使用现有五类 triage 标签。只有范围、行为和验证方式明确后才标 `ready-for-agent`，依赖外部验证时标 `needs-info`。

每阶段结束更新本页的状态与基线，链接实现 PR、验收记录和发布版本；已完成项移入完成记录，保留决策理由。若接口研究不通过，记录终止原因，而不是长期保留“快完成”的功能承诺。
