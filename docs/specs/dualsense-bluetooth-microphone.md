# DualSense 无线系统麦克风与 Codex 接入 Spec

## 当前采用路线（2026-10-18 更新）

用户安装 **DualSense Audio for macOS** 后明确反馈“效果非常好”，决定继续集成该路线。当前系统输入为 `DualSense Microphone`，不再使用旧开发桥作为日常入口。固定上游来源与构建安装见 [集成说明](../../Drivers/DualSenseAudio/JOYHARNESS.md)。以下历史 v0.2 章节保留旧桥的实验与验收要求，不代表新驱动使用说明。

- 外部语音：Options 按一次开始、再按一次结束。用户将 Options 配为语音软件的切换录音快捷键；既有映射不被升级覆盖。
- 内置 AI：按住 L2，短点 PS 开始，松开 L2 提交；PS 松开不提交，断连／停流取消。
- Game Mode：在实际采音开始前开启，最后一个系统消费者停止后恢复原策略。不会仅凭 Options 按压猜测外部软件已开麦；系统输入电平表或其他常开消费者会延长开启时间。用户此前 forced on 或期间手动更改策略时保留其选择。
- 控制：独占采音期间通过独立的只读 XPC 转发 CRC 有效的控制报告，保持 Options 与 L2／PS 可用；普通映射与体感输入暂停，旧报告与重新连接时的按住状态不变成新命令。
- 故障：Game Mode 无法确认开启时不开麦；退出／断连恢复策略，异常退出后的 journal 由 helper 重启恢复。客户端重试缺失或重启的服务。

当前自动真机检查已确认 auto/off → 录音 on → 停录 auto/off、连续系统 PCM 交付、采音期间控制流，以及 Joy Harness 中 DualSense 会话仍存在。连续 PCM 包含上游补偿，不能等同于无线零丢帧。实体 Options 两次切换与内置 AI 全流程仍需用户验收；异常退出恢复目前是软件测试证据。具体结果见[开发验证记录](../research/dualsense-microphone-implementation-validation.md)。

### 统一组件管理

通用设置已提供正式 PS5 手柄麦克风管理入口，驱动和 helper 随应用打包并分别签名，保留现有 UID 与 launchd identity。安装／更新采用管理员授权、签名固定校验、临时目录准备及失败回滚；卸载只移除 DualSense 服务和 HAL，不删除小米设备。存在待恢复的 Game Mode lease 时阻止移除。当前支持 Apple 芯片／macOS 26，并要求 Applications 中的 Xcode；不满足条件时界面说明原因。

旧预览入口与环境变量开关已退役，旧 DualSense HAL 设备随 JoyHarnessMicrophone v4 更新移除。小米设备保留原 UID 和音频缓冲契约。默认输入只能显式选择。以下历史章节仅解释实验背景，不能作为当前操作步骤。

## 历史路线：Joy Harness 自建桥 v0.2

状态：旧开发预览已落地 v0.2，音质验收未通过。

2026-10-18 真机状态：Codex 已出现波形，但中文测试句转写为 `Tu sens. Chat.`。在用户确认就绪后重新采集 30 秒，得到 12.4 秒有效解码音频；用户确认说了测试句，回听独立系统录音仍“断续、缺字或变速”。M0 音质验收失败，当前不能作为日常系统麦克风交付。

扩大 HID 队列、请求更短报告间隔、重发流命令、完整 mic-only 控制体、蓝牙重连、退出 Joy Harness 后的独立程序及独占 HID 对照均未恢复供给。低供给不依赖 Joy Harness 主程序或 HAL 消费者；尚未区分更早的蓝牙接收、系统注入与手柄实际发送。下一层内核计数受管理员权限限制。此前未赶上说话窗口的 20 秒采集只保留为数值证据。完整结果与限制见[开发验证记录](../research/dualsense-microphone-implementation-validation.md)。

后续离线比较确认，按振幅筛选的 56 个音频块在系统录音中逐样本完整保留，但片段间存在大量额外间隔。HAL 时钟周期的独立契约错误已修正，组件 `1.1.1` / `3` 已本地安装并读回生效；新版 6 秒实测仍仅提供 2.34 秒源音频，用户反馈录音后回放无声，录音应用与文件尚待确认。无线缺供及 M0 音质问题尚未解决。

2026-10-18 晚间新证据：受新开源项目启发，独立探针的 auto/off → Game Mode on → auto/off 对照，6 秒有效 PCM 依次为 2.24 → 4.61 → 2.31 秒。系统游戏策略对缺供有可逆影响，但仍未达到完整供给；应用内较高包率还触发过音频积压保护。测试结束恢复 auto/off，未将强制游戏模式自动化加入产品。替代软件与接收器路线见[研究更新](../research/dualsense-wireless-microphone.md)。

日期：2026-10-17。用户确认的最高优先级：**让 Codex 等外部应用使用 DualSense 内置麦克风作为系统音频输入**。目标版本与发布日期待定。

### 当前开发状态与验证入口

源码已加入独立 DualSense HAL 设备与 UID、48 kHz 静态 Opus 解码、原始报告分类和输入隔离、手动供音、ACT10 联动、通用设置及非激活状态面板。这些是开发实现状态，不是手柄收音、Codex 实际录音或第 8 节验收通过的证据；既定完成门槛保持不变。

软件测试、已签名预览、本机组件升级、双设备枚举与真实跨进程清空的结果见[开发验证记录](../research/dualsense-microphone-implementation-validation.md)。实际人声与 Codex 流程已开始验证，音质尚未通过。

入口仅在开发预览环境变量 `JOY_HARNESS_DUALSENSE_MIC_PREVIEW=1` 下可见。从仓库根目录运行：

```bash
env JOY_HARNESS_DUALSENSE_MIC_PREVIEW=1 bash scripts/build_and_run.sh --verify
```

启动脚本会将预览变量传给启动的应用。打开“设置 → 通用 → DualSense 系统麦克风 · 开发验证”，检查麦克风权限，显式安装或更新组件；管理员验证及音频服务重载会造成短暂声音中断。蓝牙连接一只 DualSense 并拔掉手柄 USB，选择专用系统音源或明确点击“使用 DualSense 作为系统麦克风”，再点击“开始向系统麦克风供音”。手动供音无需按手柄键；先用外部录音应用回听，再在 Codex 点击麦克风按钮开始录音，记录版本、音源选择方式及启停结果。此流程不需要启用内部 AI 语音或配置模型，也不要求刷写 RP2040。

验证 Codex 联动时，先停止手动供音，再启用“Codex 按住说话联动”并将受支持的实体键明确映射为“按住说话”；不修改既有右 Command 或 L2 + PS 入口。没有看到真实有效音频，或停止状态未确认时，记录阻断，不将设备枚举、界面存在或构建成功当作 M0 完成。

当前预览接受面键、L1/R1、方向键、摇杆按键、触控板按键和 Menu/Options。PS、L2/R2、功能层组合和系统合成按键不启用联动；不支持的来源继续遵守原映射规则，不被全局截获为新音频会话。

## 1. 产品目标与首版边界

使用 Mac 自带蓝牙接收 DualSense 内置麦克风，由 Joy Harness 解码并发布为 macOS 系统麦克风。Codex 负责自己的录音、转写和语音交互；RP2040 Plus 继续通过 USB 承担 Codex Micro 控制与灯效。

```text
DualSense 内置麦克风
  └─ Bluetooth Classic HID / Opus
       └─ Joy Harness 解码与供音
            └─ Joy Harness DualSense 麦克风（Core Audio 系统输入）
                 ├─ Codex 原生语音功能【首要验收对象】
                 └─ 其他录音、听写或会议应用

手柄的“按住说话”映射 → Joy Harness 协调音频就绪
  └─ USB → RP2040 Plus（Codex Micro 固件）→ ACT10 按下 / 松开
```

| 优先级 | 交付内容 | 完成证据 |
| --- | --- | --- |
| P0，首版核心 | 可选择的系统麦克风、显式开关收音、Codex 实际输入 | macOS 可枚举；外部录音可回听；Codex 能用手柄人声完成原生语音流程 |
| P0，首版日常操作 | 与现有 Codex Micro“按住说话”联动，保留手动供音入口 | 音频准备与 ACT10 顺序正确，首尾字完整，松开/故障无卡键和跨次残音 |
| 后续 | Joy Harness 独立 AI 语音直接消费手柄 PCM | 单独补充音源适配和验收，不作为首版前置 |

实施先打通“系统输入 → Codex”，再完成按住说话联动。若联动的可信按键门槛尚未通过，可保留已验证的手动供音能力并标记联动不可用；不能将首版整体标记完成，也不能用 Joy Harness 内部识别成功替代 Codex 验收。

本方案复用现有 Mac 与 RP2040 Plus，不要求新增硬件、改写 RP2040 固件或安装完整 ControlDeck。首版采用现有 HAL 音频组件的扩展方案；安装/更新组件是首版交付的一部分。

范围外：手柄扬声器/耳机输出、触觉音频、唤醒词、开机自动收音、游戏中同时使用手柄操作与无线麦克风，以及 Joy Harness 代替 Codex 识别或自动注入文字。

## 2. 现有契约与工程选择

按键与领域术语以 [CONTEXT.md](../../CONTEXT.md) 为基线，界面遵守 [DESIGN.md](../../DESIGN.md)。协议和公开实现依据见 [调查报告](../research/dualsense-wireless-microphone.md)。

本规格是独立的系统音频桥，**不依赖启用 [Joy Harness AI 语音](joy-harness-ai-voice.md)**。其 L2 + 短点 PS 入口、60 秒上限、模型配置及能力执行仍属于内部语音功能，不能套作外部系统麦克风的契约。

现有 `.pushToTalk` 映射为 Codex Micro `ACT10`；按下为 `1`、松开为 `0`。DualSense 当前默认 Menu/Options 路径为右 Command，不能假定默认已有 ACT10 映射。用户映射保持原样，设置中引导用户明确把一个支持的实体键绑定为“按住说话”。普通 PS、原生模式返回和现有 Harness 规则保持。

### 2.1 唯一主音频出口：现有 HAL 组件扩展

| 项目 | 首版决定 |
| --- | --- |
| 系统设备 | 新增 `Joy Harness DualSense 麦克风`，稳定 UID 为 `tech.keli.joyharness.dualsense.microphone.device` |
| 实现路线 | 扩展 `Drivers/JoyHarnessMicrophone`，在同一组件中发布独立设备；复用安装、签名及发布链 |
| 小米共存 | 保留现有名称与 UID `tech.keli.joyharness.microphone.device`；两个设备分别维护流、缓冲、时钟、客户端与会话状态 |
| PCM | Opus 解码 48 kHz mono；适配为 HAL 的 48 kHz stereo Float32，两个通道内容一致 |
| 最低系统 | 应用继续 macOS 13；分别记录目标系统与发布架构的实测结果 |
| 安装成本 | 用户显式安装/更新；管理员验证及音频服务重载造成的短暂中断须提前在安装界面说明 |
| 后续替代 | macOS 14.2+ process tap 可另行评估，首版不同时实现两套发布后端 |

现有 `RemoteMicrophoneOutput` 固定小米 UID 和 16 kHz mono 输入，不能直接传入 48 kHz 样本或创建第二实例冒充独立设备。允许复用其输出调度思想，但需显式参数化格式与路由；DualSense 不先降到 16 kHz 再升回 48 kHz。

安装检查必须验证组件版本、新 UID 和正确的输入/输出流；仅发现旧小米设备不足以显示“已就绪”。设备 UID 不随手柄重连改变，发布后空闲持续输出静音，不因手柄暂时断连删除设备。

## 3. 用户流程与界面

### 3.1 首次设置

在现有“通用”设置的麦克风区域提供 DualSense 系统麦克风入口，与小米来源清楚区分，不放在需要启用内部 AI 语音的区域。

1. 蓝牙连接一只标准 DualSense；首版先验证 `054c:0ce6`，Edge、DS4 与第三方手柄另行验证。
2. 检查 Joy Harness 麦克风权限并安装/更新自带音频组件。
3. 在外部应用选择 `Joy Harness DualSense 麦克风`。若应用使用系统默认输入，用户可明确点击“使用 DualSense 作为系统麦克风”，切换系统默认输入；成功后读回核验。
4. 点击“开始向系统麦克风供音”，无需按手柄键；看到实际 PCM 电平后，在 Codex 点击麦克风按钮开始录音，完成一次真实语音测试。
5. 如需通过手柄按住说话，先停止手动供音，再单独启用并配置 Codex 的“按住说话”联动，之后通过手柄与 RP2040 验证。

不能假设 Codex 的所有版本都有应用内音源选择器；验收记录须注明版本、选择设备的实际方式和使用的原生语音入口。Joy Harness 不猜测外部应用已经选中了哪个输入。

安装、配对、选择设备或外部应用枚举输入均不自动打开手柄麦克风。默认不改系统输入；用户显式切换的默认值持续保留，界面提供系统声音设置入口以切回其他麦克风。开关收音不反复改变默认输入。

### 3.2 手动供音：系统麦克风基础入口

“开始供音 / 停止供音”独立于 Harness、RP2040 连接和内部 AI 语音开关。用户显式开启后持续向系统设备供音，直到停止、断连或生命周期中断；不继承内部 AI 语音的 60 秒限制。外部应用用自己的录音控件管理录音。

手动供音不需要按住或按下手柄键，也不需要启用“Codex 按住说话联动”。开始供音后，用户仍需在 Codex 点击麦克风按钮开始录音；手动供音不发送 ACT10，不自动触发 Codex 录音。设置页在手动供音按钮旁直接说明这两个操作步骤。持续供音时显示常驻、可见且不抢焦点的状态与停止入口；关闭窗口不等于停止供音。停止后不因重连、唤醒或消费者再次打开设备而自动恢复。

### 3.3 Codex 按住说话联动

联动仅在用户启用、Codex Harness 生效且源手柄的可信实体键已映射为 `.pushToTalk` 时启用；其他来源的 ACT10 和原有右 Command 映射继续原行为，不全局截获并重解释。

- 按下时冻结控制器端点、物理键、映射与会话代次；先准备专用系统音频出口，再开启手柄麦克风。
- 首个有效 PCM 到达且输出可写后，重新检查按键仍被可信地按住、原会话有效、Codex Harness 与 RP2040 可用，再发送 ACT10 按下并发布该会话音频。
- 准备期间松开或失败，不发送迟到的 ACT10；显式按下之后的首帧可短暂有界缓存，按下之前不预录。首字完整性必须实测，不能用固定等待声称 Codex 已开始录音。
- 正常释放发起第5节的有界尾音排空与 ACT10 松开；异常路径停止继续供音并及时尝试释放，硬件关流不能阻塞必要释放。
- 普通 PS 和 L2 + PS 不作为此入口。只开放原始控制报告已验证支持的实体键；系统合成按键、组合动作和无法可靠读取释放的来源不能启用联动。

手动会话与按住说话会话互斥；忙碌时保留当前所有者并提示先停止，不接管、合并或悄悄再开第二路。已有内部 AI 语音会话也不能抢占该设备。输入源身份须在仍有实体键信息的入口绑定，不能只在现有仅携带 `key/action` 的全局 `keyHandler` 中推断。

### 3.4 真实状态与职责

分别显示“组件已安装”“设备已选择/选择情况未知”“正在准备”“正在向系统麦克风供音”“已停止供音”“硬件停止未确认”。供音状态以有效解码和输出链为据；静音但有效的 PCM 可以就绪，不要求用户先出声。

Codex Micro 的 CDC 发送成功只表示进入主机输出缓冲，没有执行 ACK。界面可显示音频已就绪及控制已发送，不能据此宣布“Codex 正在录音”“已提交”或“已取消”。

外部应用可能实时转写或上传已读到的 PCM。Joy Harness 的停止/取消只控制继续供音与本地尚未交付缓冲，不能撤回已经交付的音频，也不能把 ACT10 松开冒充 Codex 的取消协议。对录音、转写和云端处理的设置由消费应用负责。

未连接、USB 连接、身份不明确、权限拒绝、组件过旧、无法定向输出或协议失败时明确说明并保持静音；不自动改用 Mac 内置麦克风，不回退到扬声器。产品反馈使用设备与音源名称，协议字节、CRC 与队列信息只放诊断。UI 实现时同步更新 DESIGN.md，保留 VoiceOver、键盘操作、亮暗外观与 Reduce Motion 支持。

## 4. 协议、路由与音频契约

### 4.1 唯一设备所有权与报告隔离

同一手柄由一个 HID 所有者协调控制、音频和输出，携带连接/会话代次。HID 回调仅做有界复制、分类和单调时间记录；输入、输出写入、解码和 Core Audio 渲染分别调度，主线程不等待同步 HID 写入。

蓝牙 `0x31` 不得无条件解释为按键：在任何 mic-enable 前，统一入口按已验证的长度、传输布局与子类型分成控制、麦克风和未知报告。IOHID 单独提供或包含 report ID 的情况分别归一化，不猜字节偏移，也不套用 L2CAP 的 HIDP 前缀偏移。

所有 GameController、IOHID value 和 raw HID 路由在进入业务之前门控；音频或未知包不进入按键、陀螺仪、电量、输入高亮和控制心跳。开麦前释放原有键鼠持有状态、归零持续动作并取消 MotionJump；供音期间暂停该设备的普通映射，恢复前验证硬件关闭和可信中立，丢弃旧代次及排队动作。

按住说话的释放来自**本次发起联动的实体键**。补全其可信原始状态解析，不能沿用仅提取 PS/L2 的旧样本。控制连续性看门狗初值250 ms；音频包不能续期，停流不能被解释为正常松键。该门槛未通过时禁用联动；手动供音可在所有手柄业务输入已隔离、鼠标/键盘停止入口可用且音频验收通过时独立验证。

进入原生模式前结束供音并确认硬件关闭，包括前台应用触发的自动模式切换。关闭未确认时保留 Joy Harness 自身的故障隔离，提示关闭手柄重连；本应用不能阻止其他应用直接读取 HID。

### 4.2 启停协议与 Opus

以调查报告所列固定版本的自洽实现为参考，落实初始化、路由、mic mute、stream-open/close、序号与 CRC，不混拼不同项目的控制模板。已知 mic 变体通常含71字节 Opus，以48 kHz mono解码，每包通常480样本；完整报告常见78字节、IOHID剥去ID后77字节，只接受真实验证过的布局。

入站 CRC 及所处传输层须用真实录包确认；坏包不进入解码。出站 CRC 用独立固定向量核验。每个会话重置 decoder、包序和缓冲；重复、回绕、重排及缺包显式处理，短缺口可有界 PLC，严重异常停止供音。

灯效、扳机与 mic 控制经同一串行输出协调器，合并状态，防止覆盖音频位。开/关/重试均带代次；旧 enable 不得在取消或重连后重新开麦。同步 `IOHIDDeviceSetReport` 已阻塞时，取消 Swift Task 不代表底层调用结束；保持故障状态并禁止新开麦。

物理静音状态和实际声音单独验证；不自动解除用户静音。硬件 LED 仅作辅助反馈，不证明采集或停流事实。

### 4.3 实时音频与系统设备

解码后持续向专用 UID 输出，使用单调样本时间线适配 Core Audio 时钟、蓝牙抖动和时钟漂移；不会先录完整段再发送。渲染回调使用预分配缓冲，不做 HID、文件或网络操作。

编码和播放队列分别有界，初值各以100 ms容量评估，而非固定增加100 ms等待；记录实测延迟后锁定参数。容量用毫秒和目标采样率表达，不复制小米的16 kHz样本常量。长期积压、持续溢出、异常时钟或解码失败应停止并说明，不能以静默丢掉大段语音维持“正常”。

此前 HAL 的旧 sample stamp 能避免环形缓冲重放，但 stop 不清空数据，且消费者常开时写入端重启不一定触发全设备重置。开发实现已加入每设备清空入口；首版仍须验证完整的会话失效/清空契约：读端保持打开也能作废旧会话；缺少当前有效样本时稳定输出零。多消费者读取同一输入不互相消耗样本，两个设备不混音、不相互停流。

写入端退出或崩溃后，系统输入在有界时间内转为静音，无重复旧语音；初始验收目标为最后有效写入后500 ms内。软件取消后的静音目标为250 ms内。二者均需消费者保持录音的实测证据，不宣称崩溃瞬时清空或硬件已关麦。

### 4.4 时间与尾字

记录每包的设备/会话代次、包序、HID回调接收时间、样本数及丢失/PLC信息。当前没有已验证的麦克风硬件采样时间戳，接收时间不能冒充精确采样时间。

按住说话正常松键时，首版仅保留可信释放回调之前已完整接收的音频，之后到达的包用于停流观测并丢弃。该保守策略可能截短无线链路里的尾音，需通过外部录音和 Codex 尾字测试；不通过则继续验证时间模型，不能偷偷延长松手后采集窗口。手动停止立即作废尚未交付的本地缓冲，已被消费者读取的声音不能追回。

## 5. 生命周期与控制收尾

| 状态 | 音频与控制行为 | 离开条件 |
| --- | --- | --- |
| unavailable / idle | 系统设备存在时输出静音，不自动打开硬件 | 用户显式开始且设备/权限/出口可用 |
| preparing | 绑定所有者、隔离输入、准备输出、开mic；联动尚不发送ACT10 | 有效PCM与出口就绪；否则停止 |
| streaming | 手动模式直接供音；联动按第3.3节发ACT10后供音 | 显式停止、可信松键或异常 |
| stopping | 停止新增音频、关流；正常联动有界排尾音后释放ACT10 | 关闭及输入恢复已确认，或超时 |
| fault | 系统输入静音，必要控制释放仍尝试；隔离问题设备 | 重连后关流和中立验证通过 |

正常联动结束同时发起硬件关流与有限尾缓冲排空，尾缓冲初始上限300 ms。排空完成或到时就尝试发送 ACT10 松开，不等待蓝牙关闭确认；不能因为 stop 卡住长期保持 ACT10。只有对应会话实际发送过按下，才承担对应释放义务；重复/迟到回调不再开麦或跨会话释放。

异常、权限撤销、USB/蓝牙切换、锁屏/睡眠及退出均立即停止继续供音、丢弃待发数据并执行必要释放。切换 Harness 或修改源 PTT 映射只中断联动会话，手动供音不受影响。RP2040 暂不可达时记录未确认释放，重连先清理原持有状态再允许新联动；提示控制状态未确认，不声称板端或 Codex 已完成释放。停止手动会话不发送 ACT10。

工程超时初值：开流1.5秒无有效PCM则失败；采集中500 ms无有效音频则停止。关流立即发送，必要时100/250 ms有界重试；2秒内仍无法确认则fault。软件关闭确认要求本代次关闭写入成功、无旧开流请求在执行、可信控制状态恢复且至少100 ms无音频；它不等于硬件隐私级静音证明。各阈值是待实测校准的工程值，不是Sony保证。

输出静音、必要的 ACT10 释放与硬件关流分别完成，分别记录结果。正常退出尽力有界关流；崩溃不能保证关闭包到达手柄。下次连接先处理遗留音频和关闭，再等待新的显式开始。

手动模式不因普通前台应用变化停流；切入原生手柄模式及其他上述中断会停止。联动按 Codex Harness 门控，外部应用的实际录音/提交状态始终由外部应用拥有。

## 6. 权限、分发与共存

- 用户显式启用和授权后才开mic；原始HID不能绕过麦克风拒绝。权限检查不在应用启动时隐式弹出；撤销后停止供音。IOHID额外权限按目标系统实测反馈。
- Codex或其他录音应用需自己的麦克风权限。HAL主路线不依赖process tap，不要求其系统音频录制权限。
- 固定libopus版本、校验值及许可证，随签名应用发布；不依赖Homebrew、Python运行环境或临时下载。参考ControlDeck MIT代码时保留适用版权声明。
- 音频组件签名、架构、冷安装、旧版升级、管理员授权取消及音频服务重载均纳入交付。安装后的设备枚举成功只是中间步骤。
- 桥接本身不新增识别或网络请求、不默认保存音频；开发探针仅在用户显式开始后保存测试WAV。外部应用的数据处理按其配置执行。
- 保留小米音频、RP2040控制/灯效和未启用新音源时的既有行为。手柄断连后专用输入静音，不替换为其他物理音源。
- 内部AI语音仍按既有系统默认音源工作，不自动抢占手柄硬件。若系统默认恰为该虚拟设备而它未供音，应说明音源未就绪；直接PCM接入另行实现，不在首版暗加依赖或回路。

## 7. 实施顺序与完成门槛

### M0：无线采音与系统麦克风端到端探针

退出当前已安装 Joy Harness 及其他手柄映射程序；若在实验构建中运行，先完成全部报告分类与输入门控。记录Mac/系统/手柄固件、输入布局、CRC、解码、关流与权限结果。扩展HAL并验证专用UID，先用外部录音应用回听，再在Codex实际走原生语音流程。

**完成条件：**手柄USB拔出；系统输入可选；外部录音声音来自手柄、音高和时长正确；Codex实际收到手柄人声。仅生成本地WAV、看到电平、列出设备名称或内部AI识别成功均不足以完成M0。

### M1：日常收音与Codex控制协调

完成手动开关、音频会话所有权、独立设备缓冲、停流与恢复；补全用户PTT实体键的可信原始状态，再实现音频就绪与ACT10按下/松开的协调。保留当前映射，新增配置引导。

**完成条件：**手动供音不依赖RP2040或内部AI开关；Codex联动准备期间松键不迟到启动；正常松键首尾字完整；异常有界静音并及时尝试释放；无音频误触发和跨会话数据。控制门槛失败时联动维持不可用并记录阻塞，系统麦克风验证继续独立推进。

### M2：设置、安装与首版验收

完成真实状态UI、音源选择引导、签名分发和全部验收，记录支持组合与未测范围，更新产品契约文档。

**完成条件：**第8节P0验收完成，Codex日常语音可用，用户无需新增硬件或安装另一完整应用。最终报告分别标注系统音频、Codex联动和硬件关流结果；未验证功能不称为已支持。

## 8. 验收矩阵

自动化遵循 **No tautological tests**：协议向量来自独立真实录包或手工审定记录，不由生产构造器自证；合成音只验证格式、重采样与播放，不代替真实声源证据。

| 自动化场景 | 验收结果 |
| --- | --- |
| 控制/音频/未知、含/不含ID、坏CRC及截断包 | 正确分类，无越界/幽灵按键；音频不续控制看门狗 |
| 丢包、回绕、重复、抖动与解码失败 | 时间线与错误符合独立预期，队列有界，严重异常转静音 |
| 新旧UID、48k格式、小米16k路径、多设备/消费者 | 路由独立，格式正确，互不混音或抢走样本 |
| 消费者持续打开时取消、快速重开、生产端停止 | 旧代次失效，无旧语音；缺样本稳定输出零 |
| 准备中松键、旧enable完成、伪高层释放 | 无迟到ACT10按下，无伪正常结束或重新开mic |
| 正常尾音、stop阻塞、排空超时、RP2040断连 | ACT10必要释放不等待蓝牙；未确认状态真实；无跨会话控制 |
| 默认输入选择、缺权限/旧组件/输出绑定失败 | 仅显式操作改默认；失败不换音源或走扬声器 |

| 实机验证 | 首版完成标准 |
| --- | --- |
| 真实无线声源 | 手柄USB拔出，对照手柄/Mac距离与手柄附近语音；外部WAV确认来自手柄 |
| 系统与Codex | 系统输入可枚举；外部应用可回听；Codex实际使用该音源完成原生语音，记录版本/选择方式/权限 |
| 语音质量 | 至少20次独立短句，外部回听与Codex使用均无明显首尾字丢失、变调、重复或跨次串音 |
| 按住说话 | 至少50次开始/松开/快速按放/中断，准备无迟到启动、无幽灵映射或卡住ACT10 |
| 连续供音 | 手动显式开启10分钟，延迟/内存不持续增长，样本时长与墙钟偏差不超过1%；不中途套用60秒限制 |
| 常开消费者与故障 | Codex或录音器保持输入打开，覆盖停止、重开、断连、USB插拔、睡眠、强杀及重启；满足静音时限，无旧语音回放 |
| 静音与外部职责 | 物理静音和权限撤销生效；停止提示不声称撤回已交付音频或取消了Codex转写 |
| 共存 | 小米和DualSense分别取音不混入对方，多个消费者能读取同流，RP2040控制与灯效正常 |
| 分发与系统 | 冷安装/旧组件升级/授权取消/音频服务重载可恢复；macOS13及当前系统、发布架构分别实测或明确未验证 |

分别记录首次有效PCM、外部应用可读音频的延迟、正常松键至尾音结束、ACT10释放及硬件关闭时间。10 ms编码帧不等于端到端延迟。以上是目标，不是已取得成绩。

实现阶段运行 `task ci`、`task release-check`、音频驱动检查、签名/安装验证及 `git diff --check`。使用脱离构建目录的发布包真机复测；RP2040固件保持既有协议，不以刷写它作为音频验收前置。
