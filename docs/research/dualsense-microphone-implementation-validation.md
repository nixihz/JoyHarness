# DualSense 系统麦克风开发验证记录

日期：2026-10-17 至 2026-10-18。关联规格：[DualSense 无线系统麦克风](../specs/dualsense-bluetooth-microphone.md)。

本记录区分软件检查与实际人声录音。软件检查通过不代表 M0 通过，功能仍为显式开启的开发预览。

## 本机与现状

- 本机：arm64，macOS 27.0.1。
- 系统蓝牙清单：一只标准 DualSense 已连接，Sony `054c:0ce6`；另一只为未连接的配对记录。
- 检查开始时已安装 HAL 组件为 `1.0.0` / bundle version `1`。随后已通过应用内安装入口升级到 `1.1.0` / bundle version `2`，系统已枚举出 DualSense 与小米两个独立的 48 kHz 双通道虚拟设备。
- Joy Harness 已确认麦克风权限就绪。Codex 已有波形，但转写错误，用户确认独立系统录音断续；M0 音质验收失败，详见下面的实测记录。
- 后续离线修正了 HAL 时钟周期，组件为 `1.1.1` / bundle version `3`；用户随后要求本地安装，已安装并读回实际时钟周期 `16384`。新版本仍有无线缺供，详见本文末尾。
- RP2040 Plus 固件及 USB 控制协议未修改；新音频由 Mac 接收、解码和发布。

## 2026-10-18 首次无线供音实测

用户明确同意现在测试后，通过应用设置将系统默认输入从 `ECM-W3R` 切至 `Joy Harness DualSense 麦克风`，再显式开始手动供音。应用进入 streaming，持续显示有效 PCM 电平；后续观察值为 `0.0006490757`。这验证了当前手柄连接下的报告分类、CRC、Opus 解码及专用输出准备能够进入持续运行，但单次电平不证明人声可懂度。

已请用户在 Codex 原生语音入口说测试句。电脑操作工具明确禁止控制 Codex 自身，因而未自动操作 Codex，也未绕过该限制。用户先反馈没有波形，随后询问是否需要按手柄键；这次操作步骤未明确，不能据此认定音频故障或成功。

短暂测试结束后已通过 UI 停止供音，确认恢复为 idle（开始按钮可用、停止按钮禁用，未显示关闭故障），并在系统声音设置恢复默认输入 `ECM-W3R`。没有保存测试音频文件，没有启用 ACT10 联动。

## 独立消费者与第二轮人声检测

用户后续自行将默认输入选回 `Joy Harness DualSense 麦克风`。手动供音不需要按手柄键；Codex 本身仍须点击麦克风开始录音。设置说明、DESIGN 与规格已补上这两个步骤，PTT 联动仍关闭。

### 合成音频链路

- CoreAudio IOProc 合成 997 Hz、峰值 0.25 的输入/输出往返，读取 RMS `0.17678023`，停止后为零。
- 与真实供音相同的 AVAudioEngine mono → stereo mixer → 专用 UID 路径，长缓冲 RMS `0.1767800`，每 10 ms、480 帧逐包 RMS `0.1746731`，峰值 `0.25`；两通道可由独立消费者读到。该结果验证系统供音路径，不证明真人语音可懂度。
- FFmpeg 8.1 的 AVFoundation 输入只收到约三分之一采样量。直接 AVCapture 回调检测 5.004 秒、240192 帧、PTS 覆盖率 `1.00000`，无 PTS 缺帧；将同一回调按 FFmpeg 单槽加 10 ms 轮询模型读取，仅得到 78912 帧、覆盖率 `0.32906`。丢块来自 FFmpeg 的读取模型，不能用该工具验收音频时长或音质，也不能由此判定 HAL 丢块。

### 用户说话检测

第一次 15 秒独立检测：系统输入峰值约 `−42.47 dBFS`，整体 RMS `−68.67 dBFS`。用户随后明确表示尚未说话或错过了窗口，因此本次只能作为静音环境观察。

第二次将窗口延长到 45 秒，提示已开始后请用户连续说测试句；用户确认说完。专用系统输入峰值 `−16.41 dBFS`，短窗 RMS 峰值 `−31.40 dBFS`，无 NaN 或 Inf。声音已到达系统输入；未保存录音，尚未回听或验证转写正确性。因 FFmpeg 丢块，不能把这份结果当成时长完整性验收。

随后直接使用 AVCapture 消费同一专用 UID 60 秒：15001 次回调、每次 192 帧，共 2880192 帧；PCM 时长与 PTS 跨度均为 60.004 秒，覆盖率 `1.00000`，PTS 缺口与缺帧均为零。第一通道峰值 `0.347909987`、整体 RMS `0.004186436`。该探针仅统计数值，不保存音频、不修改默认输入、不向设备写音频，也没有直接控制物理麦克风。检测期间仍向用户请求 Codex 原生录音反馈；时间戳完整不等于已验证语音可懂度或 Codex 转写。

本轮停止曾两次出现“停止或中立状态未确认”。独立只读 HID 探针随后在 3 秒内收到 147 份控制报告，全部中立、音频报告为零；后续重试恢复开始按钮可用。复合停止条件中具体哪一项未满足尚未定位，不能将该提示等同于硬件仍在采音，也不能忽略该恢复问题。

目前仍以 Codex 的真实波形、转写及停止表现为最终验收，不能仅凭非零电平标记 M0 完成。

### 第二轮 Codex 反馈

用户已在 Codex 点击原生麦克风并完成测试，反馈“有波形，但转写不正确”。随后补充实际结果为 `Tu sens. Chat.`，与中文测试句明显不符。因此可确认消费者已经收到输入，转写验收仍未通过；不能先归因于硬件增益、蓝牙缺包或识别服务。用户已同意下一轮在本机临时目录记录解码侧与系统输入侧音频供回听，不上传。

本次结束后通过 UI 停止供音，开始按钮可用、停止按钮禁用、无停止故障；随后只读 HID 探针 3 秒内收到 164 份全中立控制、音频报告为零。没有改变用户自行选择的系统默认输入，没有启用 ACT10 联动。

操作说明修正后 `swift build -c release` 通过；使用 `JOY_HARNESS_DUALSENSE_MIC_PREVIEW=1 bash scripts/build_and_run.sh --verify` 完成签名、打包和启动验证。已检查设置页的新说明、未供音状态和关闭的 PTT 开关。没有重装 HAL 组件。

另用合成内容序列检查 10 ms buffer 调度：普通 10 ms 间隔约有 1.375 ms 内部静音间隙；0/20 ms 成对到包无内部间隙；30 ms 迟到出现约 16.8 ms 间隙，40 ms 预缓冲对照消除间隙。四组均未丢失测试信号能量，不能据此证明实际转写错误源于调度，也不作为未经真人验证的修复依据。

独立代码审查另发现当前 SDK 要求 `ZeroTimeStampPeriod ≥ 10923`，当时驱动为 `512`。该时钟属性不等于实际音频 I/O 块长度，不能用它解释 FFmpeg 丢块或当前转写错误。此次真人测试未变更或重装驱动；后续源码修正见本文末尾。

## 第三轮：实际音频帧供给不足

用户同意在本机临时目录记录短音频供回听后，同时运行独立共享 HID + 主 Opus 解码器，以及原生 AVCapture 专用输入采集，窗口约 20 秒。文件位于 `/tmp/joyharness-dualsense-voicecheck-20261018/`，没有上传。解码 WAV 连续拼接收到的有效帧，不补静音或 PLC；系统 WAV 按实际消费者采集。

| 指标 | 实测 |
| --- | --- |
| HID 时间 | 20.005 秒 |
| 控制报告 / 音频报告 | 408 / 708 |
| 音频 subtype / TOC | 全部 `0x02` / `0xd4` |
| CRC/分类拒绝、解码失败、相邻重复 payload | 全部 0 |
| 解码 PCM | 339840 帧，即 7.08 秒，仅窗口的 35.4% |
| 系统消费者 | 960192 帧 / 20.004 秒，PTS 覆盖率 100%，无缺口 |
| 解码侧 / 系统侧峰值 | 均为 `0.192588642`（Int16 WAV 量化后 `0.192596436`） |
| 系统录音中长度 ≥2 ms 的精确零值段 | 589 段，合计约 12.886 秒 |

这区分了“消费者持续收到 buffer”和“实际音频内容完整”：当前系统输入的时间戳虽完整，但真实来源只有约三分之一的 PCM，不能用之前的覆盖率证明语音链路完整。该缺供足以严重影响识别；尚待回听与进一步定位硬件/蓝牙栈的实际发送节奏。

随后做不保存声音的同时对照：默认 HID 读取队列和设置为 `MaxReportBufferCount=64`、`ReportBufferEntrySize=128` 的独立读取进程，在约 10 秒均收到完全相同的 631 份报告（217 控制、414 音频）；全部连续报告的高四位序号变化均为 `+1`（630 次），没有 CRC 或解码错误。两边 PCM 均只有 4.14 秒，设置加大读取队列未改善这次缺供。不能直接由这项结果断言空中链路无丢包，报告序号在更早层的语义仍须谨慎。

上述两轮采集后均通过 UI 关闭供音，恢复开始按钮可用、停止按钮禁用。

再做 5 秒默认与请求 `ReportInterval=1000µs` 的读取对照，两边同为 298 份报告（105 控制、193 音频），仍仅 1.93 秒有效 PCM。请求属性设置成功并读回 `1000`，结束后已恢复并读回原值 `8000`，实际报告速率无改善。带内核时间戳回调的报告平均年龄约 `0.21–0.28 ms`，最大约 `5.22 ms`，音频时间戳间隔与到达间隔分布吻合；这不支持进程内排队是主要原因。

随后在已初始化的手动供音期间，用独立串行队列尝试每 10 ms 重发现有 `microphoneStreamReport(active: true)`，不修改路由、增益、静音或 HID 队列属性。约 6.05 秒实际完成 196 次成功写入（含结束时一次 `active: false`，实际约 32 次/秒，并未达到每秒 100 次）；收到 128 份控制、240 份音频报告，解码 115200 帧，即 2.4 秒，仍只有约 39.7% 的音频供给。367 次相邻全报告序号变化均为 `+1`，CRC/分类拒绝和解码失败均为零。该对照不支持“周期性重发当前流命令即可恢复供给”，不将 keepalive 加入产品；由于实际写入节奏受限，也不能宣称已经完成 100 Hz 发送实验。

临时探针结束后发送关闭流命令，应用显示“手柄音频已停流，已停止供音”，开始按钮可用、停止按钮禁用。独立 3 秒只读检查收到 157 份全中立控制报告、音频报告为零，未改变用户选择的系统默认输入。以上对照只统计数据，没有新增声音文件。前述本机录音仍待用户回听，尚不能将数值缺供直接等同于已确认的具体听感或完整测试句内容。

再次保持初始化、state、gain 与 routing 不变，仅将 stream 命令替换为固定上游 DS5Dongle 的完整 mic-only 模板（142 字节，`32 [seq<<4] 91 01 [03=open/02=close]`、零填充和 Sony CRC），不混用部分字段。先发送原协议关闭，再发送 mic-only 开启；6.003 秒收到 127 份控制与 232 份音频报告，111360 帧为 2.32 秒，供给约 38.6%。358 次相邻全报告序号变化均为 `+1`，CRC/分类拒绝与解码失败为零。结束先发送 mic-only 关闭，再发送原协议关闭，全部 4 次输出写入成功，应用恢复已停流状态。此项仍未改善缺供，不修改正式协议；没有新增录音。

只读参考审查未发现有依据的麦克风时钟/采样率初始化遗漏：ControlDeck 麦克风仅在启停时发送控制，10 ms 定时器用于扬声器；neo 的记录明确开启可锁存，停止输出后仍收音，另记录约 99 音频包/秒；旧 bridge 的 177 音频包/约 4 秒不能当作完整音频证据。缓存 Linux 可调 BT polling 位属于 DualShock 4，不能套用到 DualSense。实际 TOC `0xd4` 与每包 480 帧一致，没有将其解释为更长音频或拉伸到墙钟时长的依据。

### 用户纠正与重连对照

用户随后明确反馈第三轮本机录音“没赶上录音窗口”，回听问题也作相同回复。因此这两段 WAV 不能作为完整测试句、人声音质或声音活动期间缺供的证据。35.4% 的帧供给及系统补静音仍是该窗口的实测，但尚不能排除声音活动相关的发送行为，也不能据此断言它就是此前 Codex 错误转写的根因。

通过系统设置断开这一只 DualSense 后，用户短按 PS 恢复蓝牙连接。重连后先只读确认 3 秒收到 181 份中立控制、无音频，再通过 UI 开始手动供音。6.010 秒对照收到 127 控制与 233 音频报告，解码 111840 帧 / 2.33 秒（38.8%）；359 次全报告序号差均为 `+1`，CRC/分类与解码错误均为零。重连没有改善这一安静场景的供给率。检测后已通过 UI 关闭供音，开始按钮可用、停止按钮禁用；未新增录音、未改变默认输入。

下一轮改为先等用户确认就绪，再开启较长但有界的本机诊断窗口，对比连续说话时的包率及两侧音频，避免再次将未说话窗口当作人声验收。

### 就绪确认后的 30 秒采集

用户回复“准备好了，开始录音”后，再通过 UI 开启供音并启动同步双侧采集；两个工具确认启动后立即提示现在说话。文件只保存在 `/tmp/joyharness-dualsense-voicecheck-ready-20261018/`，没有上传。采集 30.005 秒收到 643 控制与 1240 音频报告，解码 595200 帧 / 12.4 秒（约 41.3%）；全部音频 subtype `0x02`、TOC `0xd4`，CRC/分类拒绝、解码错误和相邻重复 payload 都为零。原生系统输入为 1440384 帧 / 30.008 秒，PTS 无缺口，两侧峰值均约 `0.14718665`。

逐秒包率为 34–45；第 5–6 秒 RMS 约 −40 至 −42 dBFS、包率 40/42，第 16–24 秒多为约 −87 dBFS、包率仍为 38–45。电平变化没有伴随接近 100 包/秒的供给恢复。用户随后明确确认“说了，但录音断续、缺字或变速”；这次人声音质验收确实失败，问题已出现在独立系统录音中，不能仅归因于 Codex 的识别语言选择。逐秒与具体测试句的对应位置仍未人工标注，不把非零电平直接作为语音片段标签。

采集结束通过 UI 停止供音，独立 3 秒检查收到 173 份全中立控制报告、音频报告为零。默认输入保持用户先前选择，PTT 联动仍关闭。

用户确认测试时手柄离 Mac 主机一米以内、无遮挡。继续检查底层接收路径及连接信息，不据此直接排除射频干扰或蓝牙栈行为。

### 脱离应用与独占 HID 对照

### 只读连接信息与下一层诊断边界

对唯一已连接 Sony `054c:0ce6` 读取 feature `0x20`，64 字节长度、ID 和 `0xA3` seed CRC 通过：hardware `0x00000711`、firmware `0x0110002a`、update `0x0630`。系统蓝牙界面的通用 `1.0.0` 不能替代该实际固件信息。
