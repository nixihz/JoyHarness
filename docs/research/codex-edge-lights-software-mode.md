# Codex 屏幕状态灯：纯软件模式可用性调研

调研日期：2026-10-14。范围是取消屏幕状态灯对 RP2040 的依赖，不包括审批、拒绝、语音等完整 Micro 控制操作。本次未修改应用、固件或 Codex 设置。

## 结论

六槽分配可以自动完成，不必要求用户手动绑定六个任务。真正影响可用性的是：自动选择的任务是否符合用户预期、槽位是否频繁换位，以及运行、等待、完成未读、已读状态是否准确。

现有 `CodexThreadProvider` 不能直接替代原生 Micro 镜像。可以实现独立的软件提醒模式，但目前证据不足以把它作为原生六槽体验的等价替代。若必须保持原生槽位顺序、阅读后立即熄灭提醒和准确的等待状态，建议暂时保留现有硬件路径。

## 六槽并不要求手工维护

本机客户端的 `codex-micro-slot-signals-6ec81e0cf251.js` 明确实现四种来源：

| 来源 | 客户端行为 | 软件复用难度 |
| --- | --- | --- |
| recent | 取最近任务的前六个 | 较低，但需匹配客户端的数据范围和排序规则 |
| pinned | 合并置顶任务、置顶项目下的任务，并应用置顶排序 | 中等；仅查询“置顶任务”不等价 |
| priority | 根据等待、未读、活跃状态和最近活动排序后取六个 | 较高，依赖准确的实时状态和未读数据 |
| custom | 使用用户指定的槽位关联，也可绑定动作 | 需要读取内部配置，或新增独立配置 |

这说明“程序自行分配”不等于“用户自行分配”。不过直接每两秒把最近六个任务按更新时间重新排序，会导致同一灯位对应的任务变化。对只有编号、没有常驻标题的灯条，这会增加识别成本；同时存在七个以上相关任务时，还要处理被挤出显示范围的任务。

可设计自动进入空槽、运行期间不换位、完成提醒保留到确认、满槽时提示还有其他任务。但这会形成 Joy Harness 自己的槽位规则，与原生 Micro 槽位不再保证一致。它是可选产品方案，不是现有能力。

## 状态来源的实测

环境：本机 ChatGPT/Codex 客户端 `26.1007.30912`，内置 CLI `0.162.0-alpha.17.2`。仅输出字段名、数量和状态统计，未保存任务正文。

### 独立 app-server

用与仓库相同的 `app-server --stdio` 启动方式完成初始化，然后只调用查询方法：

| 查询 | 结果 |
| --- | --- |
| `thread/list`，最近 20 个未归档任务 | 返回 20 个任务，20 个状态均为 `notLoaded` |
| `thread/loaded/list` | 返回 0 个 |
| 返回字段 | 有 ID、标题、路径、状态、时间、项目和 section 信息；没有原生 Micro 槽号或未读标记 |

`notLoaded` 表示该进程没有加载相应任务，不能当成“空闲”。独立进程能读取历史元数据，不代表已经接入桌面客户端的实时任务流。

仓库的 `CodexRolloutStateReader` 会补读日志中的 `task_started`、`task_complete`、`turn_aborted`。这能帮助识别开始、完成和中止，但目前没有补齐客户端未读、等待审批、等待回答及错误的完整语义，也不能据此承诺覆盖远端或云端会话。

### 已有 app-server 守护进程

只读的 `app-server daemon version` 报告本机存在运行中的 `0.160.1` 守护进程。通过内置 CLI 的 `app-server proxy` 发送初始化，8 秒内未收到响应，随后结束了本次探测进程。

这次探测没有证明可连接桌面客户端的实时状态源，也不证明该路线不可行。尚未确认这个守护进程是否就是当前桌面任务使用的进程。没有启动、重启、停止守护进程或恢复任何任务来改变实验条件。

### 公开文档与本机版本不同

[官方 app-server 文档](https://learn.chatgpt.com/docs/app-server) 描述任务列表、运行状态变化通知和 `isPinned` 过滤，并建议按所用 CLI 版本生成协议定义。

本机生成的 `ThreadListParams` 使用 `sectionId`，不含 `isPinned`，`Thread` 也不含 `isPinned`。实测发送 `isPinned: true` 仍返回 20 个任务，没有错误；因此“请求成功”不能证明置顶过滤生效，不能直接照公开示例假设兼容。

本机协议具有 `section_position` 排序和 section 查询能力，但还未验证其与客户端所有置顶项目、跨主机任务及手工顺序的对应关系。

## 原生未读与跳转

客户端打包代码表明：

- 灯色结合运行状态、approval/input attention 和 `hasUnreadTurn` 计算。
- 当前会话在应用窗口获得焦点时，未读灯可以直接显示为空闲。
- 未读数据由客户端单独管理；本机持久状态含 `electron-thread-read-state-v1`，按身份和执行主机划分。
- 置顶顺序、置顶项目和自定义 Micro 关联也存在于客户端内部状态中。它们不是一个公开的“六槽快照”接口。
- 客户端有生成 `codex://threads/<id>` 链接的代码，带有处理非本地主机的逻辑。点击跳转具有可研究的现成路径，本次没有实际打开会话验证。

读取内部文件有望复用部分状态，减少用户重复配置；但必须处理账号与主机归属、旧字段、落盘时序和升级变化。只有字段存在，还不能证明实时、一致、完整。直接复用客户端内部 IPC 或注入代码也不属于已验证、稳定的外部接口。

## 可用性判断与建议

| 目标 | 当前判断 |
| --- | --- |
| 无硬件播放光缝、呼吸和完成动画 | 可行，绘制与预览已经是纯软件 |
| 用户无需手工配置六槽 | 可行，可以自动选取任务 |
| 少量本机任务的开始/完成提醒 | 有实现基础，适合有限范围原型；需实测漏报、重启误报和陈旧状态 |
| 最近六任务自动轮换 | 可实现，但频繁换位和超出六个任务会降低辨识度 |
| 阅读后与 Codex 同步消除未读提醒 | 现有 provider 不具备；需要额外状态适配和验证 |
| 原生 pinned/recent/priority/custom 六槽完全一致 | 未找到已验证的公开快照接口，现有方案不能保证 |
| 多主机、云端与本地统一显示 | 尚未验证，不应由本机日志方案直接承诺 |

建议不直接把现有元数据列表接到灯条上作为硬件替代。如果后续验证软件模式，应先确定三项门槛：不用用户重复分配任务；等待/运行/完成状态不误报；在 Codex 其他入口读过任务后提醒能正确消除。若仍要求与 Micro 一致，还必须验证槽位逐项对应。

若只需要“任务结束时出现一次屏幕提醒”，可以采用短暂完成动画，不声称维护原生未读状态，产品复杂度会明显降低。若需要截图中的完整六槽交互，现阶段继续使用 RP2040 的成本更可控。

当前 `CONTEXT.md` 和 `DESIGN.md` 明确要求光缝读取原生 Micro 灯效、使用原生槽位；新增独立软件模式会改变这一设计约束，需要同步更新文档。本次没有改变该约束。
